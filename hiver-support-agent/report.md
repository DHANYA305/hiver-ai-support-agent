## 0. LLM-as-judge status — read this first

The assignment requires an LLM-as-judge rubric with evidence of human
agreement. The project implements Gemini-based LLM generation and judging
through `src/generation/llm_client.py` and the reply-quality evaluation
pipeline.

The Gemini client was successfully tested with a direct request:

```text
Available: True
Result: Hello there, friend.
```

This confirmed that the Gemini API integration and request wiring work.

However, when the full evaluation pipeline was run, the Gemini API quota was
exhausted (`429 RESOURCE_EXHAUSTED`). To prevent mixing LLM and heuristic
scores in the same evaluation, the final reproducible evaluation was run using
the project's heuristic fallback.

Therefore, the final evaluation reports:

```text
JUDGE BACKEND FOR THIS RUN: HEURISTIC
```

and:

```text
No usable GEMINI_API_KEY found — using heuristic fallback for
reply-quality judging. Any "LLM-as-judge" claim in report.md is INVALID
for this run.
```

As a result, **all final reply-quality and judge-human agreement numbers in
this report were produced by the heuristic fallback judge, not by a real LLM
judge**.

This is a real limitation against the assignment requirement and is stated
explicitly rather than hidden. The Gemini integration remains implemented and
was successfully tested independently, but sufficient API quota was not
available to complete the full evaluation using Gemini.

The final heuristic judge's agreement with hand-scoring was measured on 3
calibration examples:

* Exact match rate: **0.0%**
* Within-1 rate: **66.7%**
* Mean Absolute Error: **1.67**
* Spearman correlation: **-1.0**

This small calibration run should not be interpreted as strong evidence of
judge quality. Instead, it reinforces the main limitation: automated
reply-quality scores from the heuristic fallback should not be treated as
equivalent to validated LLM-as-judge scores.

## 1. Problem framing

### What "good" means for SpotifyCares support, specifically

* **Intent classification** exists to route and act, not to win a leaderboard.
  A misclassification only matters if it changes what happens next — for
  example, calling a billing question a general complaint means it may not get
  the billing-specific escalation policy.

* **A good drafted reply** is one that is faithful to a real, historically
  used brand resolution — not one that merely sounds fluent. A
  confident-sounding reply that invents a refund policy is worse than an honest
  "we'll look into it," because Twitter support replies are public and
  unretractable.

* **A good escalation decision** optimizes for catching the costly failure
  direction: auto-sending something wrong on money, security, or sensitive
  account issues. Recall on "should have escalated" matters more than raw
  accuracy.

### What we chose not to build

* Multi-turn conversation state / thread modeling — many real resolutions in
  this dataset happen over private DM, which is not visible in the public
  dataset.

* A fine-grained 20+ intent taxonomy — additional labels would not necessarily
  map to different actions for this support agent.

* Per-user personalization or account lookups — out of scope because a real
  deployment would require integration with Spotify's internal account systems,
  which the public dataset does not provide.

* A production-grade vector index such as FAISS or embeddings — deliberately
  deprioritized to keep the system lightweight and reproducible within the
  assignment scope.

## 2. Results vs. baselines

### Intent classification (n=210)

| System                                                                  |  Accuracy | Macro F1 |
| ----------------------------------------------------------------------- | --------: | -------: |
| Trivial (always predict `playback_technical`, the majority class)       |     14.8% |     0.04 |
| **Simple (keyword rules)**                                              | **88.1%** | **0.89** |
| System (TF-IDF + Logistic Regression, trained on rows excluding golden) |     71.4% |     0.68 |

**The simple keyword-rule baseline beats the trained classifier.**

This is the corrected, leak-free result. A previous version of the evaluation
contained train/evaluation leakage that made the classifier appear much
stronger. After excluding all golden examples from training, the classifier
achieved 71.4% accuracy instead of the previously inflated result.

The main reason the trained classifier underperforms is the severe class
imbalance and noise in the weak-label training signal.

---

### Escalation decision (n=210, 55 gold-escalate / 155 gold-auto-handle)

| System                      |  Accuracy | Precision |    Recall |       F1 |
| --------------------------- | --------: | --------: | --------: | -------: |
| Trivial (never escalate)    |     73.8% |         — |      0.0% |     0.00 |
| Simple (hard triggers only) |     73.3% |     44.4% |      7.3% |     0.13 |
| **System (full policy)**    | **65.7%** | **39.2%** | **56.4%** | **0.46** |

The trivial baseline has the **highest accuracy** here and is still the worst
possible system because it has 0% recall on cases that actually need a human.

This demonstrates why raw accuracy is misleading for escalation decisions.
Accuracy alone would recommend shipping the do-nothing baseline.

The full system trades some accuracy for a large recall improvement over the
simple hard-trigger baseline. It catches substantially more cases requiring
human review, but also over-escalates 48 safe cases.

This trade-off was intentional: the cost of incorrectly auto-handling a
sensitive billing, security, or account issue is considered higher than the
cost of sending a safe case to a human.

## 3. Failure analysis — top 5, with real examples

### 1. The trained intent classifier cannot learn rare classes well

`content_availability` is the extreme example: it achieved effectively 0 F1.

Every one of the 22 golden `content_availability` examples was
misclassified, mostly as `general_complaint`.

Examples include:

> "Reputation still not available on spotify ph"

and:

> "All of Anita Baker's albums are removed from Spotify... you better apologize and fix it"

The root cause is severe class imbalance in the weak-label training data.
The rule-derived training signal contains only 19
`content_availability` examples out of approximately 11,787 training rows
(around 0.16%).

Two fixes were attempted:

1. Rule-first/classifier-fallback hybrid
2. Oversampling minority classes to 1,000 rows each

Neither solved the underlying problem. Duplicating a very small number of
near-identical examples does not create new information, and the weak labels
themselves remain noisy.

---

### 2. `general_complaint` absorbs genuinely ambiguous messages

Example:

> "my account has been premium for a while now but I renewed my subscription since I changed my bank card now it keeps saying free"

This was labeled `general_complaint` but predicted as `account_access`.

This is not purely a classifier failure. It also reveals a taxonomy limitation.

The message contains multiple overlapping concepts:

* billing/subscription
* changed bank card
* premium status
* account state

A single 7-way exclusive intent label cannot always represent such mixed
customer problems accurately.

---

### 3. Escalation over-triggers on technical issues phrased in unfamiliar words

Example:

> "why is my music skipping like a cd"

This receives a similarity score of approximately 0.61 and can be correctly
auto-handled.

However:

> "iPhone after a song ends the app crashes"

describes a similar technical problem but has much lower lexical overlap with
historical examples.

Because retrieval uses TF-IDF, paraphrases that use different words may appear
less similar even when they describe the same issue.

This contributes to unnecessary escalations and is a fundamental limitation of
word-overlap-based retrieval.

---

### 4. The heuristic reply-quality judge is not trustworthy enough

The heuristic judge can reward replies that look fluent and support-like even
when they are generic.

For example, a fallback such as:

> "Hey! Thanks for flagging this — could you DM us the details?"

can score well because it has an appropriate tone and next step, even though
it provides less issue-specific help than a grounded historical resolution.

This is exactly why a validated LLM-as-judge or human evaluation is important.

The final heuristic calibration results were:

* Exact match: 0%
* Within-1: 66.7%
* MAE: 1.67
* Spearman: -1.0

The calibration sample is small, so these values should not be overinterpreted,
but they clearly do not provide strong validation of the heuristic judge.

---

### 5. Hard-trigger escalation is brittle and catches very few true escalation cases

The simple hard-trigger baseline achieved only 7.3% recall.

Most cases requiring escalation are not explicit keyword matches for terms
such as fraud, legal issues, or self-harm.

Many instead involve:

* account verification
* billing disputes
* specific personal account claims
* sensitive subscription problems

A keyword list cannot reliably identify these cases.

Even the full system misses 24 gold-escalate cases because some have neither a
hard trigger nor a sufficiently relevant historical retrieval match.

## 4. What is misleading about my headline number? (mandatory)

### Three specific, real issues we found

### (a) Train/evaluation leakage inflated retrieval-grounded results

The golden set was sampled from the same approximately 12k-row pool used to
build the retrieval index.

If evaluated naively, a golden example's own customer message remains inside
the retrieval pool.

This produced:

```text
mean_top_similarity_leaky_index = 1.0
```

This could make downstream results look nearly perfect for the wrong reason:
the system was effectively retrieving each evaluation example's own historical
answer.

The issue was fixed using:

```text
RetrievalIndex.build_eval_index(...)
```

which excludes golden examples from the retrieval pool.

After the fix:

```text
mean_top_similarity_clean_index ≈ 0.28
```

This is a much more realistic measure of retrieval performance.

---

### (b) The intent classifier was originally trained on golden examples

This was a more serious leakage problem.

Because the golden set was sampled from `pairs.csv`, and the original classifier
training step used the full `pairs.csv`, all 210 golden examples were present
in the classifier's training data.

This meant the first classifier evaluation was partially measuring
memorization rather than generalization.

The training pipeline was changed to exclude golden customer texts from the
training data.

The corrected result is:

```text
Accuracy: 71.4%
Macro F1: 0.68
```

The corrected number is lower than the simple keyword-rule baseline.

This changed the conclusion of the evaluation: the trained classifier is not
the best-performing intent system in this project.

Finding this issue was important because it demonstrates why leakage checks
matter more than simply reporting the highest metric.

---

### (c) The reply-quality headline score should not be treated as an LLM-quality score

The final evaluation reports:

```text
Mean overall reply quality: 4.07/5
```

However, this score was generated by the heuristic fallback judge, not by a
real LLM judge.

The final calibration run produced:

```text
Calibration examples: 3
Exact match rate: 0.0%
Within-1 rate: 66.7%
MAE: 1.67
Spearman: -1.0
```

The calibration sample is too small to make strong statistical conclusions, but
the results do not validate the heuristic judge as a reliable substitute for
an LLM judge.

Therefore, the reply-quality headline number is useful only as a diagnostic
metric for the current pipeline and should not be interpreted as evidence that
the system has achieved validated 4+/5 response quality.

This is the biggest remaining evaluation limitation in the project.

## 5. What I'd do with one more week

### 1. Run the full evaluation with sufficient Gemini API quota

This is the highest-priority improvement.

The Gemini integration is implemented and successfully tested, but the full
evaluation encountered API quota exhaustion.

With sufficient quota, I would rerun:

```bash
python -m src.evaluation.run_eval
```

using Gemini for:

* reply generation
* reply-quality judging
* LLM-vs-human calibration

This would replace the current heuristic judge metrics with genuine
LLM-generated evaluation results.

---

### 2. Get a second human labeler

Have another person independently label 50+ golden examples.

This would allow calculation of inter-rater agreement, such as Cohen's kappa.

Currently, the golden labels represent one person's carefully applied judgment
but are not independently cross-checked.

---

### 3. Replace weak labels with a larger hand-labeled training set

The main bottleneck for the trained classifier is the weak-label training
signal.

I would hand-label 500+ examples across all intents rather than relying mainly
on rule-derived labels.

This would provide:

* better minority-class coverage
* cleaner training signals
* less class imbalance
* more meaningful classifier evaluation

---

### 4. Add a verification step before extractive reply reuse

Before reusing a historical reply, verify that important concepts from the
customer's message are represented in the retrieved case.

For example:

* device names
* feature names
* subscription terms
* account concepts

This could prevent a superficially similar retrieval match from producing an
incorrect response.

---

### 5. Recalibrate escalation thresholds on different traffic

The current thresholds were evaluated on data from the same overall dataset
distribution.

I would test them on a different date range or separate traffic sample to
check whether they generalize.

---

### 6. Add limited multi-turn context

Even including the customer's immediately preceding message could help resolve
ambiguous cases currently labeled `general_complaint`.

A lightweight context window would likely provide some of the benefits of
conversation modeling without requiring a complex state-management system.

---

## Final conclusion

This project implements an AI support agent for SpotifyCares that:

1. Classifies incoming customer messages into support intents.
2. Retrieves historically similar customer-support cases.
3. Drafts replies grounded in real historical resolutions.
4. Decides whether a case should be auto-handled or escalated.
5. Evaluates the system against trivial and simple baselines.

The most important result of the project is not the highest metric.

It is the discovery of two real evaluation leakage issues:

1. Golden examples appearing in the retrieval pool.
2. Golden examples appearing in classifier training data.

Both were fixed before the final evaluation.

The final results also show an important practical lesson:

* The simple keyword baseline beats the trained classifier.
* Accuracy is misleading for escalation decisions.
* Retrieval can fail on paraphrases with low lexical overlap.
* The current heuristic reply-quality judge is not a substitute for a
  validated LLM judge.

The system is therefore a working, reproducible support-agent prototype with
honest evaluation limitations rather than a system optimized only to produce
impressive headline numbers.
